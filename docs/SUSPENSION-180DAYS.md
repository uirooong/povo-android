# 180 日ルール — 利用停止までの残り日数

povo2.0 の「有料トッピングを長期間購入しないと利用停止」ルールと、本アプリでの
扱いをまとめる。出典は `faq.povo.jp` カテゴリ 35（特に No.904 / No.896 / No.1378）。

---

## 1. ルール（FAQ から確定）

- カウント起点は**購入日ではなく「最後に期限が切れるトッピングの有効期限の翌日」**。
  複数持っていれば最も遅い期限が基準。
- トッピングを一度も買っていなければ **SIM の有効化（開通）から 180 日**。
- 180 日で「事前に通知のうえ**順次**利用停止」。停止後 30 日で契約解除。
- 金額を問わず有料トッピングを 1 つ買えばリセット（povo ガチャや少額でも可）。
- 紛失や未払いによる利用停止期間も**カウントは止まらない**。
- プロモコードのデータボーナスは有料トッピング購入扱いに**ならない**。
- 期間内の従量通話料 + SMS 送信料の合計が**税込 660 円**を超えた期間は対象外。

### FAQ の計算例（実装のテストに使っている）

```
A: 1月1日購入の3GB（30日間） → 有効期限 1月31日
B: 1月2日購入の1GB（7日間）  → 有効期限 1月9日
→ 期限が遅い A が基準。2月1日からカウント開始。
```

つまり **有効期限 = 購入日 + 期間**（購入日を 1 日目に数えない）。
実アカウントでも 2026-02-28 購入の 365 日間トッピングが 2027-02-28 期限になり、
2 経路で裏が取れている。

窓は「翌日から 180 日間」なので最終日は `有効期限 + 180`、
**停止予定日は `有効期限 + 181`**。

## 2. なぜ起算日をユーザー入力にしたか

API から自動導出する設計を検討したが、**どの経路も推定にしかならない**。

| 経路 | 何が足りないか |
|---|---|
| `quilt/page/user-plan-details-v2` | **現在有効なトッピングしか返さない。** 期限切れの一覧は povo 自身にも無い（FAQ No.1378 — 前日のメールとアプリ内通知だけ）。数え始めたい瞬間に起算日が消える |
| `quilt/page/order-history` | `purchase_date` はあるが、**有効期間は商品名の中の「（365日間）」という文字列にしかない**。`データ使い放題24時間` のように括弧が無いものや、`通話かけ放題` のような自動更新系は読めない |
| `notification/history/push` | 既定のパス形状で **404**。仮に通っても povo の予告は停止直前にしか来ないのでカウントダウンには使えない（未解決の手がかり） |

推定した停止予定日は、外れたときに**間違った安心**を与える。日付を出さないより悪い。
したがって起算日はユーザーが登録し、未登録は「未設定」と表示するだけで強制しない。

**660 円ルールは実装していない。** 請求から窓口期間に按分する必要があり、外すと
停止予定日を実際より後ろにずらす —— 回線が止まる方向に間違える。詳細画面の脚注に
明記して、人が判断できるようにしてある。

## 3. 実装

| 場所 | 役割 |
|---|---|
| `core-povo/.../model/Suspension.kt` | 純関数。`expiryFrom(購入日, 日数)` と `forecast(有効期限, 今日)`。`java.time` の暦日差で数える |
| `core-povo/src/test/.../SuspensionTest.kt` | FAQ の例と実アカウントの値で日付の丸め・境界を固定 |
| `app/.../data/SuspensionStore.kt` | 起算日の保存。**Room ではなく DataStore** |
| `app/.../data/SettingsStore.kt` | 表示 / 通知のオンオフ、通知日数（1〜180、既定 14） |
| `app/.../notify/SuspensionNotifier.kt` | チャンネル `povo-suspension` と投稿 |
| `app/.../ui/detail/SuspensionAnchorDialog.kt` | 登録ダイアログ（日数 / 日付の切り替え式） |

### 保存先が Room でない理由

`PovoDatabase` は `fallbackToDestructiveMigration(dropAllTables = true)`。
API から取り直せるキャッシュならそれでよいが、**手入力は取り直せない**。
スキーマを変えるたびにユーザーへ再入力を求めることになるので DataStore に置く。
`SettingsStore` がテーマについて既に同じ主張をしている。

### 通知の重複抑止

更新は 15 分ごとに走るので、素通しだと 1 日 96 回鳴る。
`SuspensionAnchor.notifiedFor` に**通知済みの停止予定日そのもの**を記録する。
フラグではなく日付にしているのは、トッピングを買って起算日を入れ直せば
日付が変わり自動で再武装されるため（フラグだと誰かが消す必要がある）。

投稿できなかった場合（権限が無いなど）は記録しない。届かなかった通知が
翌日の通知を止めてしまわないようにするため。

## 4. 未検証

- **Android 13+ の実行時通知許可**。検証に使ったエミュレータが API 30
  （Android 11）で、`POST_NOTIFICATIONS` がそもそも存在しない
  （`pm revoke` が `Unknown permission` を返す）。コード上は
  `SDK_INT < TIRAMISU` で要求をスキップする分岐に入っており、API 33+ の
  ダイアログ経路は実機で未確認。
- `exit_url` 到達時の挙動全般（本ドキュメントの範囲外）。
