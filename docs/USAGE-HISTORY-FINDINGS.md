# データ使用量の履歴 — 実機調査の結果（機能は見送り）

「データ残量の枠をタップして使用量の推移グラフを見る」機能を検討し、
**見送りと判断した**。その根拠と、再検討するときに繰り返さなくて済むように
確定した事実を残す。

数値はすべて例示用に置き換えてある（実アカウントの使用量そのものは載せない）。

---

## 1. 結論

povo が返す期間は**サーバー固定で広げられない**。

| 粒度 | 取得できる範囲 |
|---|---|
| 日次 | **転がる 31 日窓**。当日は含まない |
| 月次 | **13 ヶ月**。契約開始月から今月まで全部入る |

「契約日から日次で全部」は**永久に不可能**。月次なら今日の時点で全期間揃う。

---

## 2. エンドポイント（実在・動作確認済み）

```
GET /api/v1/quilt/page/usage-history?type=DAILY|MONTHLY
```

quilt なのでロケールセグメントなし。povo-core の `get_quilt_page_json` に
`?type=` を足すだけで届く（quilt パスは `sin`/`uuid` 装飾の対象外で正しい挙動）。

**このページはトップレベルに `widgets` と `pageWidgets` の両方を持つ。**
本体は `widgets`、`pageWidgets` は下部の注意書き。既存の
`QuiltParser.componentObjects` は `widgets` を先に見るので、そのままで正しい。

### グラフ本体 — `povo-tile-graph`

```json
{ "type": "povo-tile-graph",
  "data": {
    "title": "2026年 8月 8日~9月 7日",
    "graph_details": [
      { "time": "8日", "usage": 1.23,
        "tooltip": { "title": "2026年 8月 8日",
                     "subtitle": "データ使用量: 1.23GB" } }
    ] } }
```

- `usage` は **GB の Float**。`account/usage/plan/get`（**KB・1024 進**）とは
  単位が違う。混ぜると事故る
- `time` は表示用の短い文字列（`8日` / `9月`）だが、
  **`tooltip.title` に完全な日付が入る**ので週次への集計は可能
- MONTHLY では 13 点、`tooltip.title` は `2026年 8月`

### 集計値 — `povo-tile-usage-info`

サーバーが平均まで計算して返す。こちらで出す必要はない。

| type | 返る集計 |
|---|---|
| DAILY | 日平均、期間合計 |
| MONTHLY | 直近3ヶ月平均、直近6ヶ月平均、直近12カ月平均、期間合計 |

### 遷移元（公式アプリ）

ダッシュボードの使用量カード（`povo-tile-base-card-usage` の
`usage_history_button`）→ `UserUsageHistoryFragment` → 上記フェッチ。
DAILY/MONTHLY の切替は `type` を変えて**再フェッチするだけ**。

## 3. 期間を広げられないことの証明（実測）

| 試したこと | 結果 |
|---|---|
| `?type=DAILY&from=…&to=…` | **無視される。** 31 日窓のまま変化なし |
| `?type=WEEKLY` | `adapter failed - Usage History Quilt API Incorrect 'type' query param : WEEKLY` |

`type` の検証エラーが**サーバー自身の口から 2 値しかないと言っている**のが決定的。
公式アプリも日付範囲パラメータを送っていない（APK 静的解析）。

### 使用量系の他ページは存在しない

APK のナビゲーションマップに名前だけ載っていた 3 つを叩いた:

```
GET /api/v1/quilt/page/{plan-usage, usage-logs, data-rollover}
→ HTTP 404  {"code":404,"type":"NO_RESULT","description":"mongo: no documents in result"}
```

**サーバー上にページ自体が無い。** ナビマップに載っている＝アプリが描画できる、
という意味でしかなく、サーバーに存在する保証ではない。

過去に潰した候補も再掲（`PHASE1-FINDINGS.md`）:

| 候補 | 結果 |
|---|---|
| `GET account/usage/data/details/get` | **HTTP 491** `error_not_found_message` |
| `GET account/plan/details/get` | **HTTP 500** `error_db_transaction` |

> 調査中に **401 `Token Expired` で 3 本まとめて失敗した**。トークンは 20 分で
> 切れる。検証画面で連続して叩くときは「トークン更新」を挟むこと。
> 401 を「エンドポイントが無い」と読み違えかけた。

## 4. 数値の意味に注意

povo 自身がページ下部（`pageWidgets` の `povo-tile-bullet`）で明記している。

- **ホーム画面の残量計算とは別の数字。**
  「海外データトッピングを除き、データ使い放題やデータボーナスなどを含む
  全てのデータ消費量」であり、「データ残量を計算するための消費量とは異なります」
- 日次平均は前日から起算し**当日分を含まない**。月次平均は前月から起算し
  **当月分を含まない**（ただし月次グラフには当月が載る）
- povo 自身が「**目安です**」と言っている

同じ画面に残量と並べると足し引きが合わない。表示するなら povo の注記を
そのまま載せる必要がある。

---

## 5. なぜ見送ったか

- 求められていたのは「契約日から全期間」の推移。**日次はそれが原理的に出せない**
- 出せるのは転がる 31 日窓で、これは povo の仕様なのでアプリ側で綺麗にできない
- サーバーが平均まで返すので、**素直にグラフを出すだけでは公式アプリの再実装**に
  なり、上乗せが薄い

## 6. 再検討するなら

- **月次だけなら今日すぐ出せる**（契約開始月から全部揃う、蓄積不要）。
  転がる窓を見せずに済むのはこの形だけ
- 日次を長期に持ちたいなら、**サーバーの 31 日窓を毎回ローカルにマージ**する。
  15 分ごとのサンプリングより優れている点は、31 日ぶんの重なりがあるので
  **数週間オフラインでも欠測しない**こと。ただし過去は埋まらないので、
  始めるのが遅れた分だけ日次は失われ続ける
- 蓄積するなら保存先は Room ではない。`PovoDatabase` は
  `fallbackToDestructiveMigration(dropAllTables = true)` なので、
  取り直せないデータを置くとスキーマ変更のたびに消える
  （`SUSPENSION-180DAYS.md` と同じ論点）
- 上乗せとして価値があるのは、povo が出していないもの:
  枯渇予測（日平均 ÷ 残量）、有効期限までのペース配分、**複数回線の比較**
